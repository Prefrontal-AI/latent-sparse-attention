lsa / LSA indexer kernels

CuTeDSL Kernel Roofline

The read that picks which keys each query attends to, as lsa's LSA indexer runs it on one GPU: every kernel written in CuTeDSL, profiled with Nsight Compute at the shapes a served chunk sees, with the Triton version of each step profiled beside it.

    Overview

    A query cannot read all T keys of the context (10,485,760 at 10M tokens), so LSA's indexer picks which keys each query attends to. It emits nothing but a list of key indices - attention itself is unchanged and not on this page. Keys are clustered into buckets by Ward clustering: pools of 4 consecutive keys, merged 64 buckets to a closed 512-key cluster block, about 8 keys a bucket. A query scores bucket centroids instead of keys, picks its best p buckets (top-p, 1,024 at the served shape), and reads their keys, at most k of them (top-k, 4,096), plus the window of 512 recent keys and the 4 sink keys. N is the number of buckets, T / 8. One selection serves every head.

    What each step means

      Two jobs every chunk and every decode step does

      Maintain the index (growth)

      When a 512-key block closes, its pools go through Ward clustering into 64 buckets. For fixed and tree, at a page end the hierarchy grows: node-bucket clustering groups buckets into node buckets of 4. A chunk or a step that closes nothing skips this job.

      Read the index (per query)

      Estimate a threshold, scan the buckets for those above it, score the candidates, pick the top-p and expand them to keys, then add the window and the sink. Every query does this, in prefill and in decode.

      Three designs

      Flat

      Scores every visible bucket, N of them, with one fused scan. The cost is linear in the context.

      Fixed

      Groups buckets into node buckets of 4, one level above them. A query keeps a beam of 2,048 node buckets and scores only their children, 2,048 x 4 = 8,192, instead of every bucket. Level 0 picks the buckets.

      Tree

      The same node buckets of 4, with levels that keep growing with the context. The beam starts at the lowest level of at most 32,768 node buckets, keeps 2,048 per level on the way down, and level 0 picks the buckets.

      Only the fixed and tree reads use the start-level keep, the beam step, the top-p pick and node-bucket clustering. Decode reads flat by default, and fixed or tree can descend instead.

        Two flowcharts, one for a prefill chunk and one for a decode step. Both start by maintaining the index, then read it. Follow the arrows from the top.

        How to read these

        • A CuTeDSL kernel. Its border and shape give its stage. Select it to jump to its card. The time is its measured duration at , or marked with an @ context where it only ran at a smaller one.
        • A torch operation. It is not a CuTeDSL kernel.
        • A decision. Each exit is labeled with the answer and is taken only for that answer.
        • A solid arrow is always taken. Its label is what flows along it, with the shape. R is the 32,768 queries of a chunk, N the visible buckets, p the top-p of 1,024, B the requests of a decode step.
        • A dashed arrow is taken only under the condition printed on it.
        • A loop arrow: the box repeats, here once per level of the tree.
        • A dotted frame groups steps that share a setting, such as the CUDA graph. A letter on a kernel says where its CuTeDSL kernel runs: H on Hopper only, B on Blackwell only, T in Triton on this GPU, which has no CuTeDSL kernel for the step.

        Prefill chunk

        One chunk is R = 32,768 queries. N is the number of visible buckets.

        Decode step

        The flat read runs inside the CUDA graph. Growth runs eagerly before the forward, when a block closes or a page end grows the tree. The descend read, for fixed and tree, is eager. Expansion (by threshold) and the descend kernels are not profiled at decode, so their boxes carry no time.

        Kernel cards

        Costs are evaluated at the served shapes: R = 32,768 queries, N = T / 8 = 1.31M buckets at 10M tokens, index dim d = 64, top-p p = 1,024, top-k k = 4,096. The measured rows come from the profile, one column per context.

        The roofline

        Each point is one kernel launch at one context. Intensity is FLOPs per byte moved at DRAM, or at L2. Height is achieved FLOP/s. A point near a roof is limited by it.

        Filled markers are CuTeDSL launches. A hollow marker of the same shape is the Triton version of that step at that context: its launches summed, FLOPs and bytes over their time. A thin line joins it to the nearest CuTeDSL point of the same step and context.

        Kernels

        Method

        Profiler
        Nsight Compute, --set full, --clock-control none so the GPU runs at its boost clock, cache flushed between passes. Each kernel is one replay, so durations are single samples.
        Arms
        Both arms are profiled on identical inputs. The Triton arm goes through the same front doors with kernels="triton", so a step's inputs, shapes and contexts match, and only the kernels behind the door differ.
        Inputs
        Synthetic, built at the served shapes: a 32,768-query chunk, index dim 64, top-p 1,024, top-k 4,096, window 512, sink 4, buckets of 8 keys, 64 buckets a 512-key page, beam 2,048 of node buckets of 4, 32,768 start nodes.
        Counters
        FLOPs come from the FP32 instruction counters and the tensor-pipe operation counters. Bytes come from the DRAM, L2 and L1 traffic counters. Intensity is FLOPs over bytes at that level.
        Roofs
        H200 specification: 989.4 TFLOP/s bf16 tensor, 494.7 TFLOP/s tf32 tensor, 66.9 TFLOP/s FP32, 4.8 TB/s HBM. Dashed lines are what a copy and a cuBLAS bf16 GEMM measured on this machine.
